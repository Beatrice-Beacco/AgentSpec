What this is

A bench for the rule engine. You give it rules and one action the agent wants to take, and it tells you whether the action gets through, which rule stopped it, and why.

It runs the real ControlledAgentExecutor — the same class the agent uses in production — but drives it with a scripted FakeListLLM instead of a real model. So there is no API key, no cost, and no randomness: the same input always gives the same verdict. That is what makes it usable as a regression tool after every step in plan.md.

The tool is a stub that records its input and returns "OK". Nothing you type is ever executed — os.remove in the action box deletes nothing.

Prior steps (collapsed) is intermediate_steps — the trajectory so far. Most code predicates ignore it; embodied ones read it. It becomes central in Sprint 4, when rules start reasoning about execution paths.

Reading the result

VerdictMeans
ALLOWEDThe tool was reached. No rule blocked it — either none fired, or one fired with enforce none.
STOPPEDA rule fired with stop. The run ended before the tool.
SKIPPEDA rule suppressed the action, but fed an observation back so the agent kept planning.
NO ACTIONThe agent never proposed a tool call. Usually a malformed script.

“Why — per rule”

The panel that matters. For each rule it shows, in order:

  1. whether the trigger matched this tool call
  2. each check and what it evaluated to (with the raw value when the predicate is negated)
  3. the enforcement, and whether the rule fires

A rule fires only when the trigger matched and every check is true — check is an implicit AND. If your rule isn't firing, this panel tells you which half is wrong.

Probe all predicates

Runs every registered predicate ({{ predicates|length }} of them) against your input and shows which return true. Use it the other way round from normal: type an action first, see what fires, then write a rule around it.

Rule syntax

rule @name                 ← identifier, no spaces
trigger
    python_repl            ← must equal the tool's .name EXACTLY
check
    involve_system_file    ← predicates, implicit AND
    submit_post_request
enforce
    stop                   ← stop | skip | none | user_inspection | llm_self_reflect
end

Prefix a check with ! to negate it. Paste several rules into the box and they are evaluated in order — which matters, see example 8.

Known grammar limits

These are rejected by AgentSpec.g4 even though the repo's own rule files and README use them. It is why 21 of the 42 shipped rules do not parse (make audit), and a large part of the case for Cedar.

You writeWhat happens
// a commentno comment token exists; lexer error
check Trueonly lowercase true is a token
trigger Gmail.SendMailevents are bare identifiers; no dots
trigger A | Bno alternation operator
trigger turn onno multi-word events (though the runtime supports them)
trigger anyANY is a dead token — declared, never used by the parser
check p & qno &; separate the names with whitespace
enforce llm_self_examinethe README's name; the grammar wants llm_self_reflect
a predicate not in the token listthe 36 names are baked into the grammar; adding one needs an ANTLR regen

And they fail open. A rule with any of these errors still loads and simply never fires — Rule.from_text installs no error listener. Watch the red parse banner under the rules box; the bench surfaces what the framework swallows. Example 7 demonstrates it.

The Cedar decision panel

Every run also asks the Cedar engine about the same call, against the policy set in policies/. It is a decision, not a second agent run, so what you see is exactly what agentguard would act on:

Allow / DenyCedar's own answer, and the enforcement outcome it resolves to
agrees / differsagainst the legacy verdict above. A disagreement is the interesting result, not a bug in the bench
context.flagswhat the Python sensors materialised — the impure half of the split. Cedar expressions are pure, so a regex like destuctive_os_inst runs here and arrives as a flag
diagnostics.reasonsthe policies that determined the decision, with their @advice and the AgentSpec rule they came from

The panel currently knows one sensor and two policies, so expect it to differ from the legacy engine on anything else — that gap is the S2.1/S2.7 worklist. Two things worth trying: example 3 (no rules loaded) still gets a Cedar Deny, because the policy set is ambient rather than passed in; and example 7 (a rule that does not parse) takes the legacy run down with an ERROR while Cedar still decides.

The engine toggle and compare mode

The dropdown next to Run picks which guard engine decides the run: legacy, cedar, or compare both. It chooses the executor directly rather than through $AGENTGUARD, so compare mode can build one of each in the same process.

Compare both runs one input through both engines and marks every row that differs. A differing row is a finding, not a bug in the bench — it is either a gap in the policy set or a real semantic difference. Three of the entries in docs/findings.md started as a row in this table. Two worth trying:

example 1both engines STOPPED, but what decided differs: @block_file_deletion (a rule) against @no_destructive_os_call (a policy)
example 3the engines disagree — ALLOWED against STOPPED. AgentSpec takes its rules as an argument, so an empty list means no guard; AgentGuard’s policy set is ambient, so the call is still denied

The Cedar panel’s diagnostics.reasons column is the raw, positional id Cedar returns; @id is what a human wrote. They differ if the policy file is reordered, which is why the outcome is resolved through the advice lattice rather than by taking the first one (see S2.8).
