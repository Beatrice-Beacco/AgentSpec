### What each one means

**unregistered predicate** — The rule names a predicate that no sensor produces. **These rules cannot fire in AgentSpec either** -- `RuleInterpreter.eval_predicate` does `predicate_table[name]` and raises `KeyError` mid-run. This is not a limit of the target language; it is the corpus and its registry having drifted apart (docs/findings.md D-3).

**non-invoke trigger** — `trigger state_change` -- the rule fires on a world-state change rather than a tool call. The schema declares one action, `invoke`. Adding `action state_change` is straightforward, and on its own it would rescue nothing: every rule in this group is blocked by at least one other cause as well.

**config enforcement** — `real:obstacle:Min_stop_distance = 10` -- the enforcement assigns a planner parameter rather than permitting or forbidding an action. Cedar has no equivalent and should not: this is not access control, it is configuration. Arguably these rules are out of scope for a guard entirely.

**parameterised predicate** — `v_f_disL(10)` -- a predicate with an argument. Our sensors are nullary: a sensor produces a named flag, and a flag has no parameters. This *is* a limit of the design, and a real one; see the ladder below for what lifting it would buy.

**does not parse** — One rule's check clause is an English sentence (docs/findings.md D-9). Accepting it would mean accepting arbitrary prose.

## The failures partition — they are not a long tail

Every failing rule is counted here against the *complete* set of causes blocking it. There is no long tail and no partial credit: the 44 failures fall into four groups and nothing sits between them.

| rules | blocked by | to rescue them |
|---:|---|---|
| **23** | unregistered predicate | one change (but 23 detectors to write) |
| **19** | config enforcement, non-invoke trigger, parameterised predicate | all three changes, together |
| **1** | config enforcement, non-invoke trigger | both changes, together |
| **1** | does not parse | nothing — it is prose, not a rule |

The second column is why the ladder below has rows that rescue nothing. A rule blocked three times is not three-quarters of the way to compiling; it compiles when the last of the three lands, and not before.

## What would raise the number

Cumulative: each row assumes every row above it. The last column is where the corpus would land.

| change | rescues | coverage |
|---|---:|---:|
| *(today)* | — | **18/62** |
| write the 23 predicates the corpus names but never registers | +23 | **41/62** |
| also add `action state_change` to the schema | +0 | 41/62 |
| also support parameterised sensors | +0 | 41/62 |
| also express planner-parameter assignment | +20 | **61/62** |

**The two middle rows rescue nothing at all, and that is the finding.** Adding `action state_change` to the schema is an afternoon's work, and on its own it moves the number by zero: every rule that needs it also needs planner-parameter assignment, which is the row that should not be implemented. Those 20 rules are all-or-nothing, and the 'all' includes a change this design should refuse.

Read the table as three claims:

1. **41/62 is the honest ceiling for the corpus as it stands.** The largest single cause of failure is the corpus naming predicates nothing registers — rules that were already dead in AgentSpec, since the interpreter raises `KeyError` on them mid-run. Writing those predicates is not a Cedar problem; the identical work would be needed to make AgentSpec itself run them. It is also the only row here that is purely labour: no design question, just 23 detectors nobody wrote.

2. **The last row is the apollo corpus, in its entirety, and it is asking for a different tool.** All 20 of those rules trigger on world-state changes and enforce by assigning planner parameters; 19 of them also test parameterised predicates. Assignment — `real:obstacle:Min_stop_distance = 10` — is the blocker that matters, and it is not access control in any form: it neither permits nor forbids anything, it tunes a controller. Supporting it would mean deciding that a guardrail language should also be a configuration language. That is a design question rather than an implementation gap, and this project answers it 'no', which makes **the realistic target 41/62 rather than 61/62.**

3. **One rule can never compile**, because its check clause is an English sentence (D-9).

## The other corpus, and what the contrast shows

| corpus | rules | compile |
|---|---:|---:|
| shipped `.ar` / `.rule` | 62 | 18 (29%) |
| LLM-generated | 20 | **20 (100%)** |
| LLM-generated, *not* counting the 22 predicates they define themselves | 20 | **0** |

Same compiler. The generated rules compile because each record carries the Python source of its own predicates; the hand-written corpus mostly does not because it names predicates that live somewhere else, or nowhere.

**This is not evidence that a model writes better guardrails than a person.** The generated rules were produced together with their detectors, so they cannot drift from them; the hand-written corpus was not, and did. It is an argument about how a rule language should be packaged, not about who wrote the rules.

It also does not mean those 20 policies are usable. `policies/generated/llm/` validates and **will not load**: the schema beside it declares the flags, but no sensor produces them, and the engine refuses a policy it could never fire. Deploying them would mean registering model-written Python as sensors.

## Threats to this number

* **It counts rules, not coverage of risk.** A corpus of 62 rules where 18
  compile says nothing about whether those 18 are the important ones. RQ2 and
  RQ3 measure that; this does not.
* **Whole-file parsing is a stricter measure and is not used here.** Two corpus
  files contain unmarked prose between rules (D-8), so no grammar parses them
  end to end. Splitting on `rule @` is how a compiler reads them, and how this
  is counted.
* **The compiler was written against this corpus.** It handles `act` prefixes
  and `llm_self_examine` because this corpus contains them. A different corpus
  would find different gaps, and the number would move.
* **Compiling is not enforcing.** A compiled policy still needs sensors that
  produce its flags. The 18 do; the 20 LLM ones do not.
